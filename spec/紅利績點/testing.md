# 會員 07 桌消費紅利積點測試計畫

## 目的與範圍

確認一位新註冊會員登入後，在 07 桌訂購兩種餐點各一份；訂單完成且已付款後，依實付金額正確累積紅利點數。測試包含會員及管理員查詢、付款與完成的時序，以及重複更新不重複累點。

本文件為測試計畫，不代表測試已執行或通過。點數及 API 規則參考 [會員紅利後端規格](./backend.md)。

## 測試環境與準備

1. 使用**獨立的暫存 SQLite 測試資料庫**及測試服務或測試程式，禁止連接、寫入或覆蓋正式的 `data/pos.db`。不使用正式會員或實際交易。
2. 以 `initialize_database` 初始化獨立資料庫，並確認測試服務的下單、會員及管理 API 均連至該資料庫；既有測試程式可參考 `tests/test_member_loyalty.py` 中對 `main.DB_PATH`、`members.DB_PATH`、`admin.DB_PATH` 的設定。若透過 FastAPI 應用程式生命週期啟動服務，初始化路徑也必須指向同一測試資料庫。
3. 確保測試資料中下列商品均供應且價格固定；確認生效的規則為每消費 10 元累積 1 點。若不符，先在**測試資料庫**設定好，再開始測試。
4. 準備尚未註冊的測試專用台灣手機號碼、符合系統限制的測試密碼及測試管理員登入。勿在計畫、測試結果或版本庫記錄真實帳號與密碼。
5. 確認新會員初始可用點數為 0；本次訂單不使用點數折抵。記錄測試環境、執行時間及訂單識別碼，以便核對歷史。

## 測試資料與預期計算

| 項目 | 測試值 |
| --- | --- |
| 桌號 | `07` |
| 餐點一 | 美式陽光早午餐盤（`sunny-plate`），220 元 × 1 |
| 餐點二 | 楓糖厚鬆餅（`pancake-stack`），185 元 × 1 |
| 訂單總額 | 405 元 |
| 點數折抵 | 0 點，折抵 0 元 |
| 應付金額 | 405 元 |
| 點數規則 | 每 10 元得 1 點，不足 10 元捨去 |
| 完成且付款後預期 | `405 // 10 = 40` 點；新會員可用餘額為 40 點 |

## 測試步驟與驗收

| 步驟 | 操作 | 預期結果 |
| --- | --- | --- |
| 1 | 使用測試資料註冊會員，完成後登入。 | 註冊成功並可登入；會員點數查詢顯示可用 0 點。 |
| 2 | 以該會員身分選擇 07 桌，將兩種指定餐點各加入一份，不輸入折抵點數，送出訂單。 | 訂單成功建立；桌號為 `07`，兩筆明細數量均為 1，總額及應付為 405 元，折抵為 0；狀態為 `received`、付款狀態為 `unpaid`。記錄訂單編號。 |
| 3 | 在會員點數頁查詢餘額及異動紀錄。 | 可用餘額仍為 0；沒有該訂單的累點紀錄。 |
| 4 | 管理員在訂單處理將該訂單付款狀態改為 `paid`，暫不改為 `completed`。 | 更新成功；會員可用餘額仍為 0，該訂單沒有累點紀錄。 |
| 5 | 管理員將該訂單狀態改為 `completed`，保留付款狀態 `paid`。 | 更新成功；會員可用餘額為 40 點。異動紀錄中該訂單恰有一筆 `earn`／「消費累點」`+40` 點。 |
| 6 | 在後台「會員管理」搜尋該測試會員並查看點數紀錄。 | 顯示同一會員可用 40 點，且可查到同一訂單的 `+40` 點累點紀錄。 |
| 7 | 再次對同一訂單送出 `completed`／`paid` 狀態更新，重新查詢會員及後台。 | 更新不重複累點：可用餘額仍為 40，該訂單仍恰有一筆 `earn`／`+40` 紀錄。 |

可使用會員頁及後台畫面執行；若以測試程式核對，使用 `POST /api/members/register`、`POST /api/members/login`、`POST /api/orders`、`PATCH /api/admin/orders/{order_id}`、`GET /api/members/me/points`、`GET /api/members/me/points/transactions` 及 `GET /api/admin/members/{member_id}/transactions`。會員與管理員須各自使用對應 session。查詢交易歷史時，應按訂單 ID 和 `kind=earn` 過濾並檢查全部分頁。

## 通過條件與結果記錄

- 所有步驟皆符合預期；訂單實付 405 元且完成付款後可用點數為 **40 點**。
- 完成及付款同時成立之前不累點；重複更新後該訂單仍只有一筆 40 點累點。
- 會員與後台查詢的餘額及訂單累點紀錄一致。
- 結果記錄包含執行日期、測試環境、訂單識別碼、每步實際結果、通過／失敗及錯誤訊息；不得記錄密碼或正式顧客個資。若失敗，保留隔離環境中的必要診斷資訊供追查。

## 測試後處理

確認紀錄完成後，停止測試服務並僅清理本次建立的隔離測試資料庫與測試 session；不得刪除或修改正式資料。若測試失敗需要保留證據，先記錄保留位置與原因，再依環境政策處理。
